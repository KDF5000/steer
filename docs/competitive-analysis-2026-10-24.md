# Steer 产品竞争力调研与批判性分析

调研日期：2026-10-24。代码基线：`115f8e0`。

## 结论

Steer 已经具备有价值的产品底座，但目前更接近“有特色的早期 Agent 工作台”，尚不足以证明有独立市场地位或可持续商业护城河。

“多 Agent + 本地/远程 + Chat + 成果预览 + 自托管”已经是拥挤赛道的共同能力。飞书入口也已有直接竞品。继续围绕这些功能数量扩展，很容易陷入长期追赶。

更值得验证的方向是：**面向已有复杂开发环境的个人和小型研发团队，让不同厂商的 Agent 安全、可恢复地使用既有机器，并交付可审查的结果。** 这里真正有价值的是环境复用、执行可靠性与结果交接，而不是聊天界面本身。

这是一项待验证的定位假设，不能当作已经成立的市场事实。当前最缺的证据是：哪些用户会持续使用、为什么放弃原生工具、是否愿意为维护这一层付费。

## 研究边界

- 阅读项目 README、产品设计、架构、部署、Task API、飞书集成，以及实际前后端、数据库模型和关键测试。
- 对外部产品优先查阅官方网站、官方文档和原始仓库；表中能力为官方公开声明，未逐一安装实测。
- 未启动完整 Steer/Relay 栈，未运行真实 Runtime、故障注入或性能基准；“存在实现”不等于“达到生产可靠性”。
- 未获得用户访谈、活跃度、留存、付费和获客数据，因此不估算市场份额，不以 GitHub stars 代表产品成功。
- 竞品没有在所读页面提及某功能，不等于没有该功能。本文区分公开能力、代码证据和分析推断。

## 1. 当前项目到底是什么

### 1.1 产品与架构

Steer 是多厂商 Agent 的工作入口，Relay 是执行基础设施：

`Web / 飞书 / Task API → Steer Server → Relay Server → 用户机器上的 Node / Runtime`

Steer 保存项目、会话、Agent 配置、运行投影和成果索引；Relay 负责执行、机器连接、容量和工作目录准备。AI 本身的推理、工具能力和很多权限行为仍来自各 Runtime。

它的价值主张可以表述为：用户保留已有机器、目录、依赖和认证，通过一个入口调用不同 Agent，并保留工作记录与成果。

### 1.2 已有实现与实际边界

| 能力 | 代码证据 | 判断与边界 |
| --- | --- | --- |
| 多机器和 Runtime 管理 | `server/internal/api/runtime_bindings_test.go`、`runtime_capacity.go`、`node_credentials.go` | 有所有权、逻辑绑定和容量模型；基础设施价值明确，但执行依赖 Relay |
| 本地目录与 Git 工作区 | `server/internal/api/server.go`、`workspace.go` | 支持已有目录和可复用 worktree；已有目录原地执行，Git worktree 也不等于安全沙箱 |
| 多厂商 Agent 切换 | `server/internal/api/tasks.go`、`project_node_test.go` | 有同机切换与可见历史补充；不等于完整迁移各 Agent 的隐藏状态、工具会话与记忆 |
| 临时委派与结果回传 | `server/internal/api/tasks.go`、`delegation_test.go` | 独立子会话、引用快照、结果回流；共享执行目录，父子任务可并行 |
| Task API | `docs/task-api.md`、`server/internal/api/tasks.go` | 有 scope、幂等、SSE、取消和续接；具备作为业务接入层的潜力 |
| 飞书 | `server/internal/api/feishu.go`、`docs/feishu-integration.md` | 项目选择、话题续接、图片、最终回复流式输出、状态卡片；配置需要创建并发布飞书应用 |
| 文件与代码结果 | `app/fusion/page.tsx`、`lib/review.ts`、`workspace.go` | 已有文件浏览、图片、文档和 diff；检查工作区接口仅提供 list/read/diff/git-status |
| 用户和 Workspace | `server/internal/store/auth.go` | 多用户各自拥有私有 Workspace；未见完整成员邀请、角色和项目级授权模型 |
| 知识与工作记录 | `server/internal/api/library.go` 和相关路由 | Skills、文档、笔记、工作日志等已存在；是否构成高频需求仍待验证 |

文档存在漂移：`docs/architecture.md` 仍称 SSE 是后续工作，但 `server.go` 已注册流接口；文档称 Runtime 单 Workspace 占用，但当前 binding 模型已支持同一物理 Runtime 连接多个所有者 Workspace。评估应以实现和测试为准，并更新这些描述。

官网列出的 Runtime 包括 Codex、Trae、Claude Code、OpenCode、Pi、Qoder 和 QwenWork。这里验证到的是 Steer 的路由和产品接入设计，未验证每个适配器在真实版本上的能力一致性。

## 2. 竞争格局

竞争要按用户任务区分。用户既可能选择同类工作台，也可能直接留在原生 Agent、使用 SSH/tmux，或自己写一个机器人。后几种替代方案经常比“另一家平台”更难击败。

| 产品 / 替代方案 | 官方公开能力 | 与 Steer 的竞争关系 | 对 Steer 的含义 |
| --- | --- | --- | --- |
| Codex / ChatGPT 桌面端 | SSH 远程项目、访问远程文件和命令、移动端接入、跨主机会话与 Git 状态交接 | 单一厂商用户的强替代 | “支持远程机器”已不足以让 Codex 用户迁移；Steer 需要证明跨厂商的收益超过新增部署与维护成本 |
| Claude Code Remote Control | 从手机/浏览器继续本地会话，服务器模式，多会话、worktree 与容量控制 | Claude 主力用户的直接替代 | 不能再按“官方只能单会话远控”的旧印象比较 |
| Happy | 多 Agent、桌面与手机、远程服务器持续执行；公开强调端到端加密 | “已有机器 + 多 Agent + 远程操作”直接竞品 | 多机器和自有环境不是空白市场，隐私叙事还需要面对 E2EE 对比 |
| Happier | 多 Agent、跨端同步、权限审批、自托管 relay、定时任务、E2EE | 极接近的多厂商控制层 | 仅增加 Runtime 数量很难形成优势；安装、审批、恢复与跨端完成度更重要 |
| AionUi | 多 CLI Agent、WebUI、飞书等消息入口、定时任务、文件预览与内置 Agent | 中文市场、办公与多 Agent 工作台的直接竞品 | 飞书、多模型和成果预览不能单独作为独有卖点；需要比较真实执行环境和任务完成体验 |
| Conductor | 多种编码 Agent；独立分支/worktree，并支持同工作区多 Agent | 代码并行与 Review 场景竞品 | 对开发者，分支、测试、审查和落地比统一聊天更影响效率 |
| OpenHands Agent Canvas | ACP 多 Agent、本地/远程 VM/云后端、自托管和扩展 | 架构与定位高度重叠 | “开放、多 Agent、远程执行、自托管”这一整组组合也已有竞争 |
| OpenCode Web / Server | 浏览器会话、headless HTTP 服务、TUI attach 同步状态 | 愿意统一到一个 harness 的用户的低成本替代 | 不是所有用户都需要管理多个 harness；统一模型与统一 Agent Runtime 是不同问题 |
| SSH + tmux + 原生 CLI | 复用已有机器与登录环境 | 高技术用户的基线方案 | Steer 必须明显减少操作与排障成本，否则会增加一层故障来源 |

## 3. 我们的竞争力，哪些成立，哪些被高估

### 3.1 成立的产品价值

**复用真实环境，能解决有成本的问题。** 私有网络、已认证工具、GPU、特定系统、长期服务和本地数据，都可能使云端重新搭环境变得昂贵。Steer/Relay 的机器与目录模型切中了这类需求。但是否比原生 SSH 与 OpenHands 更好，需要实测；“我能远程跑”只是入场资格。

**Web、飞书和 API 复用一条执行链，是较好的架构资产。** Task API 与 Web 复用任务提交逻辑，飞书也进入同一任务系统。业务系统触发任务后，用户有机会回到工作台跟进。注意，这证明的是统一后端基础，不代表所有渠道之间已经有无缝接管体验。

**跨 Agent 的引用、作者身份和结果回流比下拉框切模型更有意义。** 主 Agent 实现、另一 Agent 审查、再交回主 Agent，是一个可理解的工作流。当前已有明确实现。值得围绕这一任务验证质量和时间收益，而不是只展示能运行多少个 Agent。

**Steer 与 Relay 解耦有长期维护收益。** 可以分别演进执行基础设施和产品体验。但对用户的收益只有在安装、升级和排障简单时才成立；服务数量本身不构成优势。

### 3.2 被高估的优势

| 常见自我判断 | 批判性判断 |
| --- | --- |
| Chat-first 是差异化 | 它是交互选择。大量竞品已有会话入口，不能形成防御性 |
| 多 Agent 是护城河 | 接入数量容易同质化，适配成本却会随版本和权限协议增长 |
| 远程执行很独特 | 官方原生工具和开源产品均已覆盖；机会在恢复、环境复用与治理质量 |
| 飞书适合中国市场，因此能突围 | 有渠道价值，但 AionUi 已公开提供；更深的授权、审查与组织流程才可能提高替代成本 |
| 自托管意味着更安全 | 自托管改变控制权，不自动提供沙箱、最小权限、加密与审计；托管失误也会增加风险 |
| Artifact 面板可以成为壁垒 | 文件预览已普遍存在；版本、来源、接受/回滚、复用和交付记录才可能形成资产 |
| Workspace 等于团队产品 | 当前更接近个人多空间模型；团队共用、授权与责任归属仍需建设 |
| 架构扎实就能商业化 | 架构降低实现风险，无法证明获客、留存与付费成立 |

## 4. 当前最值得正视的问题

### 4.1 定位横跨三类人，但每类人的关键需求不同

开发者希望有 Review、测试与 PR 闭环；非技术办公用户希望免配置、可预测交付；平台管理员希望有身份、授权、审计和维护工具。当前分别做了一部分，也容易同时承担三条产品线的复杂度。

建议先聚焦“有多种 Agent、有既有远程环境的技术用户”。办公和企业平台作为后续验证方向，不要仅凭预览面板和飞书入口就扩大定位。

### 4.2 首次成功任务之前，用户要承担不少运维工作

即使有 Compose，用户仍涉及 Steer、Relay、数据库、Node、CLI 安装与登录、网络地址、密钥和权限配置；飞书还需要开发者后台配置与发布。已有原生工具用户的比较对象可能只是启用一个远程连接。

核心指标应是“新用户多久完成第一项真实任务”，而不是“安装命令有几行”。建议提供单机轻量路径、连接预检、可定位到具体组件的错误提示和升级诊断；不要过早强迫个人用户理解全部基础设施对象。

### 4.3 委派共享文件系统，但缺少显式的写入协作边界

`delegation_test.go` 明确验证父会话可以在子会话执行时提交 `parallel write`，同时要求委派共享原工作目录/worktree。这意味着会话锁没有阻止两个不同会话同时改同一组文件。

这不是已经观察到的数据损坏事故，而是代码模型允许的风险：审查基线可能变化，修改可能相互覆盖。优先建立“共享目录默认单写者，审查者通过 Runtime 权限保持只读”；需要并行写时使用独立 worktree，再提供合并与冲突处理。只在 prompt 写“不要修改”不足以构成可靠只读。

### 4.4 看见 diff 与安全接纳改动之间还有距离

现有工作区检查接口为只读操作，已经具备查看成果的基础；未见显式的分块接受、拒绝、checkpoint、回滚或合并产品接口。Agent 可以通过 shell 执行 Git，但那不等同于用户可预测的产品操作。

已有目录中的改动可能已经发生，“Accept”若只是视觉状态，会误导用户。应明确：哪些已写入、哪些待合并、撤销影响什么，以及测试针对哪个文件快照运行。

### 4.5 企业叙事领先于团队授权模型

`store/auth.go` 按 `owner_user_id` 查询 Workspace；本次未见完整的成员/角色/项目级授权。飞书消息处理记录 senderId，但在检查的入口链路中未见按飞书发送者映射 Steer 身份并授权项目的模型；目前还需要依靠飞书应用可见范围等外部限制。

这不是“任何外部用户都能越权”的已验证结论；它意味着在推广组织共享前，应明确哪些人能让哪个 Agent 使用哪些机器、目录与凭证，并保留操作者记录。Workspace 数据隔离也不代表共享 Node 上的 OS 用户、文件与凭证已经隔离。

### 4.6 可靠性的承诺应比文案更克制

飞书文档已经明确多副本 pending-event 恢复没有跨副本租约与去重协调，严格一次回复要求建议单 worker。重要工作流测试需要显式配置 PostgreSQL，并使用模拟 Relay，不调用真实 AI Runtime。

这是一套合理的测试分层，但还不足以证明多天持续执行、Node 重连、权限等待、服务升级、产物过期和凭证失效时的体验。应建立真实 Runtime 兼容矩阵与恢复验收，而非只宣称 provider 已接入。

### 4.7 自托管与隐私的表述需要精确

会话正文在服务端数据库保存，集成密钥有单独加密；本次未见会话端到端加密设计。Happy/Happier 将 E2EE 作为公开卖点。Steer 可以主张部署与数据控制权，但不应声称中间服务无法读取会话，也不能由自托管推导出模型请求不离开设备。

### 4.8 开源承诺和维护成本还有基础问题

官网强调 open source，但本次在项目文件中只找到字体授权文件，未见项目根许可证。若要以开源吸引采用，应先明确 Steer 与 Relay 的许可证及第三方依赖边界；“代码可见”不能代替明确授权。

当前 `app/fusion/page.tsx` 约 8,840 行。文件长度本身不是质量结论，但它集中了承载大量产品行为的迹象；继续追加知识库、日志和集成时，要注意核心会话体验的修改与回归成本。

## 5. 更可行的定位与商业假设

建议定位：**让不同 Agent 在你的既有机器上接力完成工作，并把每次修改变成可审查、可恢复的交付。**

初始目标人群：同时使用两种及以上 Agent，并且已有远程 devbox、Mac mini、私有网络环境或专门算力的技术用户。这里的“及以上”只是招募筛选条件，不是市场规模判断。

先验证两个场景：

1. **开发接力**：在远程环境实现修改 → 异厂商 Agent 审查同一 checkpoint → 主 Agent 修复 → 用户审查并落地。
2. **飞书触发的既有环境任务**：在授权项目中执行查询、诊断或报告任务 → 保留对话与文件 → 必要时到 Web 继续处理。

第一个场景验证跨 Agent 是否产生实际收益；第二个验证是否能把已有机器能力带给日常工作流。先选其中留存更强的一个做深。

商业化假设是：用户更可能为省去维护、可靠常驻、组织授权与审计付费，而不是为多一个聊天窗口付费。可探索托管控制面 + 自有 Node；在没有付费访谈前，不建议据此确定套餐或价格，也不建议先承担出售模型算力的成本结构。

## 6. 优先级建议

| 优先级 | 工作 | 解决什么问题 | 验收方式 |
| --- | --- | --- | --- |
| P0 | 共享工作区的单写者/只读委派边界 | 防止跨会话并行写破坏交付 | 对同一目录发起父子写任务，验证阻止或隔离；审查只读由执行权限约束 |
| P0 | 首次接入预检与可解释错误 | 降低部署与 Runtime 登录摩擦 | 新用户从空环境完成真实任务，记录耗时和人工介入 |
| P0 | 权限等待、离线与恢复状态 | 避免用户面对“似乎还在运行”的黑盒 | 真实 Runtime 下断网、重启、拒绝权限后能明确恢复或失败，不重复执行 |
| P0 | 修正文档漂移、明确许可证 | 让产品承诺可信、可采用 | 文档与 binding/SSE/委派一致，许可证明确 |
| P1 | checkpoint、diff、测试和落地闭环 | 将成果查看变为可靠交付 | 用户能知道测试基线、接受范围及恢复方式 |
| P1 | 飞书身份与项目授权 | 支撑共享使用 | 未授权用户不能列举或执行受限项目，执行记录可归因 |
| P1 | 真实 provider 能力矩阵 | 减少“统一接口”隐藏的差异 | 逐项验证取消、恢复、图片、权限交互、工具事件和产物 |
| P2 | 成员角色与组织审计 | 在真实团队需求出现后支撑付费 | 由设计伙伴验证角色与审批链，不先做泛化企业平台 |

暂缓：继续堆 provider 数量、泛化多 Agent 编排、扩展大量办公模块，以及以独立原生手机 App 作为第一增长项目。这里并非这些功能没有价值，而是当前更需要证明核心工作流能稳定降低总成本。

## 7. 如何在 4–6 周内证伪或确认定位

以下是建议实验门槛，不是现有数据，也不是行业标准。

- 招募 8–12 位符合目标特征的真实用户，至少包括多 Agent 个人用户和少量能接触真实组织环境的技术负责人。
- 使用用户自己的任务，比较 Steer、其现有方案，以及一个最接近的直接竞品。采用交叉顺序，记录安装成本和熟悉度，避免只比较漂亮 demo。
- 记录：首次任务成功耗时、人工救援次数、任务完成率、跨 Agent 交接后的返工、每周主动使用和停用原因。模型质量差异与工作台故障分开统计。
- 可暂设体验目标：首次任务中位耗时不超过 15 分钟；两周后至少一半用户仍每周主动使用；目标接力任务的人工操作时间比原方案减少约 30%，且返工和模型成本没有明显恶化。
- 单独验证付费：让设计伙伴对具体的托管/维护或治理服务做出真实试付费承诺，不能用“觉得不错”代替。
- 若大多数用户不需要跨厂商，优先收窄为某个高价值渠道/环境工作流；若普遍觉得部署成本超过收益，先改善分发和接入；若主要需求来自 API，可将 Relay/Steer 接入层作为另一条商业假设。

最终要回答的不是“我们比别人多多少功能”，而是：**对哪一类用户，Steer 能稳定减少多少环境配置、执行监督和结果交接的成本，以及这种收益是否足以驱动持续使用与付费。**
